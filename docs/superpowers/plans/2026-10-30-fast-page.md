# fast: per-commit speed page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure every first-parent commit on `main` since `v1.0.0` on hostlab (instructions per request under
callgrind, plus approximate rps) and publish the results at https://v.rustapi.cloud/fast/ as a chart + table.

**Architecture:** `benches/fast/` holds a bench server (V), a load client (C, epoll), `measure.sh` (one commit →
one JSON line), `results.py` (which commits to measure, merging, publishing a complete setup) and `run.sh`
(timer entry). A static page (`page/index.html` + `page/fast.js`) reads the published `results.json`. hostlab runs
a clone under `/opt/viltrum-fast/` from a systemd timer; nginx serves `/fast/` on the existing vhost.

**Tech Stack:** V 0.5.2 (`/root/v052/v/v`), C (gcc 11), bash, Python 3.10 stdlib only, valgrind/callgrind (apt on
hostlab), vanilla JS + inline SVG, systemd, nginx.

**Spec:** `docs/superpowers/specs/2026-10-30-fast-page-design.md`

## Global Constraints

- Zero third-party code committed: no chart library, no wrk, no Python packages outside the stdlib.
- hostlab live services: never bind 8080, 8081, 8090, 8095, 3096, 18082 or any port in use; never stop
  containers; never `apt-get autoremove`. The bench server listens on **127.0.0.1:28090** only.
- V version is the CI pin, 0.5.2, at `/root/v052/v/v`, built with `-prod`.
- Scenarios, exactly: `baseline` = `GET /baseline11?a=1&b=2`; `json` = `GET /json/50?m=1` with
  `Accept-Encoding: gzip`; `pipelined` = `GET /pipeline`, 16 requests per write.
- Commits: first-parent `v1.0.0..origin/main`, excluding subjects starting with `chore(release):`.
- Skip key is (hash, setup); `benches/fast/SETUP` holds the setup version (starts at `1`). A setup change
  re-measures every commit; the page shows only a setup that covers every listed commit.
- rps is labeled "≈" and visually secondary; delta coloring threshold ±1% vs the previous `ok` commit.
- Page footer says "Inspired by fast.vlang.io" with a link.

## Review Focus

1. A commit that does not build, or a server that crashes under valgrind: recorded as `build_failed` /
   `run_failed`, the run continues with the next commit, the page shows a gap. (Task 3 + Task 5 tests.)
2. The timer firing while a multi-hour backfill runs: the second run exits at once on the lock. (Task 4.)
3. Port 28090 already taken when a measurement starts: measurement records `run_failed`, kills nothing it did
   not start. (Task 2.)
4. A reader fetching `results.json` while it is being rewritten: files are written to a temp name and renamed.
   (Task 3 test.)
5. `main` rewritten or a measured commit no longer on first-parent `main`: it is not published. (Task 3 test.)

### Task 1: Bench server and load client

**Files:**
- Create: `benches/fast/server.v`
- Create: `benches/fast/load.c`
- Create: `benches/fast/smoke.sh`

**Interfaces:**
- Produces: server binary reads env `FAST_ADDR` (default `127.0.0.1:28090`) and `FAST_DATA` (path to
  HttpArena's `dataset.json`); routes `GET /baseline11`, `GET /pipeline` (`text 200 "ok"`), `GET /json/:count`
  with `viltrum.gzip` — handlers copied from `git show v1.0.0:benches/httparena/main.v`, TLS listeners dropped,
  `app.listen(addr)` instead of `serve`. Must compile unchanged at `v1.0.0` and at `main` (the `json` module
  decode from 1.0 is fine on 0.5.2).
- Produces: `load HOST PORT PATH [-c conns] [-p depth] [-n requests | -d seconds] [-H header]` — keep-alive,
  counts complete responses by parsing status line + `Content-Length`; prints exactly one line
  `requests=<n> errors=<e> seconds=<s.sss> rps=<r>`; exit 0 only when `errors=0`. With `-n`, sends exactly n
  requests in total and waits for n responses (depth requests per write).

- [ ] **Step 1: Write `smoke.sh`** — builds `load.c` (`gcc -O2 -o load load.c`) and `server.v` against a given
  VMODULES dir, starts the server with `VILTRUM_WORKERS=1`, runs
  `load 127.0.0.1 28090 /baseline11?a=1\&b=2 -c 1 -n 1000`, `... /pipeline -c 1 -p 16 -n 1600`,
  `... /json/50?m=1 -c 1 -n 200 -H 'Accept-Encoding: gzip'`, and asserts each line has `requests=` equal to n
  and `errors=0`; stops the server; exits non-zero on any mismatch.
- [ ] **Step 2: Run it on hostlab before the code exists** — `bash benches/fast/smoke.sh <vmodules>`;
  expected: fails (no `load.c`).
- [ ] **Step 3: Implement `load.c`** — one thread, epoll, non-blocking sockets, request bytes built once.
- [ ] **Step 4: Implement `server.v`.**
- [ ] **Step 5: Run smoke at `main` and at `v1.0.0`** (VMODULES dir with `viltrum` → `git archive` of each);
  expected: both exit 0.
- [ ] **Step 6: Commit** `feat(fast): bench server and load client`.

### Task 2: measure.sh — one commit to one JSON line

**Files:**
- Create: `benches/fast/measure.sh`
- Create: `benches/fast/SETUP` (content `1`)

**Interfaces:**
- Consumes: Task 1's server and `load` (`load` binary built once per run, passed in as `$LOAD`).
- Produces: `measure.sh <repo-dir> <hash> <work-dir>` prints exactly one JSON line to stdout:
  `{"hash":"<full>","setup":"<SETUP>","status":"ok|build_failed|run_failed","ir":{"baseline":N,"json":N,"pipelined":N},"rps":{"baseline":N,"json":N,"pipelined":N}}`
  (`ir`/`rps` omitted unless `ok`). Logs go to stderr. Exit 0 in all three statuses.

Method per scenario (values pinned):
- Build: `git -C repo archive <hash>` → `work/<hash>/viltrum`, `VMODULES=work/<hash>/vm` with symlink,
  `/root/v052/v/v -prod -o work/<hash>/server benches/fast/server.v` (server.v from the run's checkout, not
  from the commit). Failure → `build_failed`.
- If anything listens on 28090 → `run_failed`.
- Ir: `VILTRUM_WORKERS=1 valgrind --tool=callgrind --callgrind-out-file=work/<hash>/cg.%p taskset -c 0 server`;
  warm up with 500 requests (json: 100); `callgrind_control -z`; load with `-c 1`: baseline `-n 20000`,
  pipelined `-p 16 -n 20000`, json `-n 2000`; `callgrind_control -d`; Ir = the `totals:`/`summary:` count of the
  new dump ÷ n, rounded to an integer. One valgrind process serves all three scenarios in turn.
- rps: server normally with `taskset -c 0-3`, client `taskset -c 4-7`, `-c 64` (pipelined `-p 16`), `-d 3`,
  median of 3 runs, rounded.
- Always kill the server it started (trap), delete `work/<hash>`.

- [ ] **Step 1:** Implement `measure.sh`.
- [ ] **Step 2: Repeatability check on hostlab** — run it twice on `main`'s HEAD; expected: `status":"ok"` both
  times and each `ir` value within 1% between the runs. If not, raise warmup/n until it is and note the values.
- [ ] **Step 3: Failure path** — run on a hash where `server.v` cannot build (e.g. create a temp commit in a
  scratch clone that breaks `viltrum.v`); expected: one line with `"status":"build_failed"`, exit 0.
- [ ] **Step 4: Port-taken path** — `nc -l 127.0.0.1 28090 &` then run; expected `run_failed`, the `nc` still
  alive afterwards.
- [ ] **Step 5: Commit** `feat(fast): measure one commit`.

### Task 3: results.py — selection, merge, publish

**Files:**
- Create: `benches/fast/results.py`
- Test: `benches/fast/test_results.py` (`python3 -m unittest benches/fast/test_results.py`)

**Interfaces:**
- Produces pure functions (no git inside them):
  - `select_commits(log: list[tuple[str, str, str]]) -> list[dict]` — input `(hash, iso_date, subject)` oldest
    first (from `git log --first-parent --reverse --format=%H%x09%cI%x09%s v1.0.0..origin/main`); drops
    `chore(release):` subjects and sets `version` (`"v1.14.0"`, parsed from that subject) on the nearest earlier
    kept commit. Returns `[{hash, date, subject, version?}]` oldest first.
  - `pending(commits: list[dict], results: list[dict], setup: str) -> list[str]` — hashes with no result for
    `setup`, oldest first.
  - `publish(commits: list[dict], results: list[dict], current_setup: str) -> dict | None` — the highest setup
    (compare as int) whose results cover every commit in `commits`; returns
    `{"setup": s, "commits": [commit merged with its result, newest first]}`, or `None` if no setup covers all.
  - `write_json_atomic(path: str, obj) -> None` — temp file in the same dir + `os.replace`.
- CLI: `results.py pending|add|publish` with `--repo`, `--results` (JSON list store), `--setup`, `--out`;
  `add` reads one line from Task 2 on stdin. `publish` keeps the previous `out` file when `publish()` returns None.

- [ ] **Step 1: Write the failing tests:**
  - `test_release_commits_dropped_and_version_attached`: log `[(a,…,"Merge pull request #110…"),
    (b,…,"chore(release): 1.14.0 [skip ci]")]` → one commit `a` with `version == "v1.14.0"`.
  - `test_pending_skips_same_setup_only`: result for `a` with setup `"1"` → `pending(..., "1") == []`,
    `pending(..., "2") == ["a"]`.
  - `test_publish_prefers_complete_newer_setup` / `test_publish_falls_back_while_new_setup_incomplete`:
    setup 2 covers 1 of 2 commits → publishes setup 1.
  - `test_publish_drops_commits_not_on_main`: a result whose hash is not in `commits` is not in the output.
  - `test_failed_commit_published_with_status`: a `build_failed` result counts as covering and is published
    with its status and no `ir`.
  - `test_write_json_atomic_leaves_no_temp`: after the call the dir holds only the target file, content parses.
- [ ] **Step 2:** Run; expected: fails (module missing).
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Run; expected: all pass.
- [ ] **Step 5: Commit** `feat(fast): result selection and publishing`.

### Task 4: run.sh — the timer's entry point

**Files:**
- Create: `benches/fast/run.sh`

**Interfaces:**
- Consumes: Task 2 `measure.sh`, Task 3 CLI.
- Behavior: `flock -n /opt/viltrum-fast/run.lock` (exit 0 when held); `git -C /opt/viltrum-fast/repo fetch
  origin && git checkout --detach origin/main` (scripts run from this checkout); build `load`; read `SETUP`;
  for each hash from `results.py pending` (oldest first): `nice -n 10 ionice -c3 measure.sh … | results.py add`,
  then `results.py publish --out /opt/viltrum-fast/www/results.json` after every commit (the page fills in during
  backfill); copy `page/*` into `/opt/viltrum-fast/www/`. Paths come from env `FAST_HOME` (default
  `/opt/viltrum-fast`).

- [ ] **Step 1:** Implement.
- [ ] **Step 2: Lock check on hostlab** — start one run, start a second within seconds; expected: the second
  exits 0 immediately with a "busy" line on stderr.
- [ ] **Step 3: Commit** `feat(fast): timer entry point`.

- Produces in `fast.js`: `delta(prev: number, cur: number) -> {pct: number, cls: "up"|"dn"|""}` (`up` = more

Layout (layout B from the mockup): title "viltrum: fast"; one subtitle line ("Every commit on main, measured
on hostlab · inspired by fast.vlang.io"); **three small charts side by side (one per scenario, own y-scale,

for `build_failed`/`run_failed` are gaps; then the table newest first: short hash → GitHub commit link, date,
subject (+ version badge), Ir per scenario with delta, `rps ≈` muted. Footer: method in two lines, setup number,
link to `benches/fast/README.md`, "Inspired by fast.vlang.io". Colors as CSS tokens with a dark-mode block;
no horizontal page scroll at 375 px (table scrolls inside its own container).
